## Hardware GUI diagnosis, 21 October 2026

The user uploaded the workbench firmware and reported 12 V connected. The
actual MATLAB GUI connected to the FTDI COM11 interface at 460800 baud.
All hardware tests in this follow-up kept the driver disabled; no ARM/START,
motor command, NVS write, or firmware upload was performed by the agent.

- The original app reproduced a 9.52 s maximum test-loop delay and 0.255 s
  median in a 20 s recording. Its two reception paths could enter the same
  parser: a serial byte callback and the session polling timer. Packet parsing,
  many small table allocations, immediate status/log writes and plot refreshes
  competed for MATLAB's event thread.
- Reception now has one polled owner with a reentry guard and bounded reads.
  Framing uses delimiter slices, CRC uses the JVM implementation when present,
  and samples are decoded/concatenated once per poll. Logging/status UI writes
  are deferred to the display timer. Binary recording retains received raw
  data; loading recordings also decodes in batches.
- A 60 s passive GUI run received 15008 samples at about 249.7 samples/s.
  Median test-loop delay was 0.056 s. A subsequent 45 s run received 11340
  samples at 249.9 samples/s, median 0.057 s, 95th percentile 0.184 s, maximum
  0.977 s. These measure a pause/drawnow test loop, not certified button-to-MCU
  stop latency. Startup/rendering can still block MATLAB temporarily.
- Firmware output remained zero; the MCU reported zero stream-queue drops.
  The 60 s and 45 s runs still had respectively 8 and 2 invalid link frames.
  Independently parsing saved wire data confirmed occasional damaged frames;
  CRC rejection and timestamps expose losses. Zero MCU drops does not mean
  the entire host link is lossless. Frequency analysis must check gaps.
- Real passive raw bursts returned 1000 ADC samples and about 250 mechanical
  samples in 0.5 s. One capture had one ADC gap, median interval 499 us,
  maximum 1038 us and 4.02% interval jitter. The app correctly rejected its
  full interval for uniform-sampling analysis. Use contiguous span explicitly
  selected measured samples around losses; spectrum/filter preview then
  passed on a later real capture. Raw files remain unchanged.
- Current output was around 2509 mV with about 64-66 mV standard deviation
  in these captures. This is observed voltage variation, not a calibrated
  current accuracy or motor-current measurement. Noise sources were not isolated.
- The live profile had no countsPerRev, pendDownRaw or incremental arm center.
  The old animation required both calibrated angles and therefore froze.
  The new twin shows an explicitly labelled relative pendulum preview before
  calibration, and explains why the arm stays fixed until scale AND center
  exist. Geometry tests cover quarter-turn arm motion, pendulum motion and
  invalid-sensor hiding. The weak-field warning remains visible.

No native MATLAB crash occurred in these follow-up runs. The exact native
crash reported by the user was not recovered (there was no crash dump from
today). Removing callback contention addresses the reproduced lag; it does
not certify that every possible native renderer crash is fixed.

## Not physically validated

Powered motor experiments, actual stop delay/protection thresholds, calibrated
current accuracy, encoder scale, mechanical dimensions, electrical probing,
and real plant parameter estimation were not performed in this follow-up.

The software build does not validate current ratings, analog protection,
timing guarantees, PCNT interrupt behavior at maximum edge rates,
actual PWM/output truth table, waveform distortion, stop delays, thermal
behavior or protection thresholds. Measure these in coordinated commissioning.
MCU task watchdog reset is a fallback; the external STBY pull-down must handle
reset/panic independently.

## Deliberate implementation choices

- Recorded sample batches are appended to binary storage while streaming,
  instead of invoking HDF5 initialization inside a heartbeat callback. Typed
  tables are reconstructed on load; CSV/MAT exports are available.
- Default live rates are 50/100/250 Hz. Full mechanical burst is 500 Hz;
  raw ADC target is configurable up to 2000 samples/s. No untested higher
  bandwidth or PWM-carrier spectrum is advertised.
- Current ADC acquisition uses timestamped task notifications and calibrated
  conversion of the same raw sample; it does not claim DMA timing precision.
- Only one supported causal biquad section is deployed at a time. Butterworth
  design is second order. Offline zero-phase processing is never deployed.
- Motor actuation uses bounded signed duty and standby disable. Separate
  active braking, position/speed servos and upright balancing are outside
  this characterization release.
- Interactive simulator time is bounded per GUI update. Its synthetic clock
  can advance slower than wall time; it must not be used to benchmark hardware
  communication/scheduling.
- Live graphs update at up to 5 Hz. Sensor acquisition and recording remain
  independent. Analysis plots retain ordinary axes interactions; continuously
  updating live axes omit default mouse interactions/toolbars to reduce work.
- Filter design can explicitly resample a valid contiguous dataset to a nearby
  nominal rate (within 5%). MCU filter deployment requires its exact nominal
  ADC rate; original sampling quality is retained in the comparison report.
- Nonlinear parameter fitting requires explicit geometry/electrical constants
  and bounds; missing/insufficiently identifiable parameters are not invented.
- Bode/step views apply to fitted linear models. A nonlinear physical fit
  requires a separately justified linearization before such analysis.
